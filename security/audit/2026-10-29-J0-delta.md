### The osv-scanner change

The scan is now `osv-scanner --config=osv-scanner.toml --no-call-analysis=go --recursive .`
(`Makefile` audit target, `security.yml`).
- **`--no-call-analysis=go`** makes the scan stricter. Without call analysis,
  osv-scanner reports every advisory on a required module and cannot drop any as
  unreachable. It replaces a run that died with exit 127 on `tools/go.mod`, a module
  with no packages.
- **The ignore** (`osv-scanner.toml`) covers GO-2026-5932 only, until 2027-01-31,
  with a written reason. I checked that reason independently at HEAD:
  - `go list -deps ./...` and `go list -deps -test ./...` find no `golang.org/x/crypto/openpgp` package.
  - `go list -modfile=go.mod -deps tool` in `tools/` and `go list -deps tool` in
    `tools/actionlint/` find none either.
  - The 17 `openpgp` packages that the tools compile are all `github.com/ProtonMail/go-crypto/openpgp/*`,
    a different module that the advisory does not cover.

  The ignore is therefore valid. What it lacks is an issue number, so it is added to SEC-J0-14.

## New findings

### SEC-J0-25 (low, cat 5): the network guard sees direct stdlib and x/net imports only
- **Location:** `.golangci.yml:55-79` (depguard `network`) and `internal/httpx/boundary_test.go:25-38` (`networkPkgs`).
- **Evidence:** I added a probe file in a throwaway copy of HEAD (scratchpad, deleted
  afterwards). golangci-lint reported no depguard or forbidigo issue, and
  `TestModule_NetworkOnlyThroughHTTPX` did not flag it:
  ```go
  fd, _ := syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM, 0)
  _ = syscall.Connect(fd, &syscall.SockaddrInet4{Port: 443, Addr: [4]byte{1, 1, 1, 1}})
  return exec.CommandContext(ctx, "<external HTTP client binary>", "https://example.invalid").Run()
  ```
  Third-party HTTP clients also get past both guards, because they only check direct imports.
  A connector could import a scraping or REST library, for example, or `internal/dest/gdrive`
  could import the Google API client, which builds its own `http.Client`. Both would bypass
  the allowlist. Hard rule 6 (ADR per dependency) is the only control left for this path.
  No such code exists today, so this is a guard gap and not a violation.
- **Fix:**
  - Add `syscall` and `golang.org/x/sys/unix` socket use to the guard, either with a
    forbidigo pattern `^(syscall|unix)\.(Socket|Connect|Dial.*)$` or a depguard deny with an
    allow for `internal/proc` and `internal/fsx`.
  - Add `os/exec` to depguard, allowed only in `internal/secret/bitwarden`.
  - In `boundary_test.go`, add a transitive check with `go list -deps -json` per production
    package outside `internal/httpx`: any path to `net` must go through `internal/httpx`
    or through a reviewed allowlist of modules.

### SEC-J0-26 (low, cat 6): the fsx-only guard misses `os.OpenRoot`, `*os.Root` methods and raw syscalls
- **Location:** `.golangci.yml:30` and `.golangci.yml:34` (forbidigo `os.` patterns).
- **Evidence:** the same probe compiled and was not flagged by forbidigo or depguard. Only
  wrapcheck complained, about unwrapped errors, which is unrelated:
  ```go
  r, err := os.OpenRoot("/tmp")
  f, err := r.Create("pwn")
  _ = r.WriteFile("pwn2", []byte("x"), 0o644)
  wfd, _ := syscall.Open("/tmp/pwn3", syscall.O_CREAT|syscall.O_WRONLY, 0o644)
  _, _ = syscall.Write(wfd, []byte("x"))
  ```
  Files written this way escape the `fsx` guarantees (0600/0700, atomic writes, SafeName).
  `docs/security.md:158` states that "`internal/fsx` is the only package that writes files".
  A grep finds no `os.OpenRoot` outside `internal/fsx` today, so this is a guard gap.
- **Fix:** add `^os\.(OpenRoot|NewFile)$` to the forbidigo fs patterns and
  `^(syscall|unix)\.(Open|Openat|Creat|Write|Pwrite|Rename.*|Unlink.*|Mkdir.*)$` (exempting
  `internal/fsx` and `internal/proc`). Add a lint-probe test that pins the rule, similar to
  `TestNetworkViolations_Detector`.

### SEC-J0-27 (medium, cat 8): build and scan tools are fetched at floating versions in CI
- **Location:**
  - `.github/workflows/release.yml:20`: `goreleaser/goreleaser-action@e435ccd… # v6.4.0`
    with `args: release --clean` and no `version:` input.
  - `.github/workflows/security.yml:18`: `go install golang.org/x/vuln/cmd/govulncheck@latest`.
  - `.github/workflows/security.yml:19`: `go install github.com/securego/gosec/v2/cmd/gosec@latest`.
  - `.github/workflows/ci.yml:17`: `go install mvdan.cc/gofumpt@latest`.
- **Evidence:** the action is SHA-pinned, but the goreleaser binary it downloads is not.
  `docs/adr/0001-tools-pinning.md` says so itself: "`release.yml` runs `goreleaser-action`,
  which picks the goreleaser version itself; pinning it there (`version: v2.12.7`) needs a
  workflow edit by Florian."

  That binary runs in a job with `contents: write` and `id-token: write`
  (`release.yml:5-7`). A compromised or regressed goreleaser release would therefore build
  and keyless-sign the facto artifacts with the repository's identity.

  `@latest` scanners in the CI gate break the "pinned versions" control: a CI run is not
  reproducible, and its result can differ from `make audit`, which uses the
  `tools/go.mod` pins of ADR 0001. The previous J0 report wrongly counted "31 `uses:`,
  0 unpinned" as full pinning, and missed the `@latest` installs.
- **Why medium:** "pinned versions" is a rubric control of category 8, and the release job
  holds signing rights. It is not high, because the action's SHA pin limits who controls
  the download logic, and no release has been cut yet.
- **Fix:**
  - Set `with: { version: v2.12.7, args: release --clean }` in `release.yml`, to match the
    `GORELEASER_IMAGE` pin.
  - Run `make tools`, then `govulncheck` and `gosec` from `tools/go.mod` (`go tool -modfile=tools/go.mod …`)
    in `security.yml`, or at least pin `@v1.9.0` and `@v2.30.0`. Do the same for gofumpt.
  - Add `make release-check` to `ci.yml`.
